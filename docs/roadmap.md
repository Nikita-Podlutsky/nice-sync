# Этапы и идеи

| Этап | Результат и проверка |
|---|---|
| 1. Локальный архив | Rust CLI индексирует тестовую папку, сохраняет файл и версии. Тесты проверяют повторное индексирование, извлечение старой версии и сохранение архивной копии после удаления источника. |
| 2. Связь двух узлов | Перенести установление защищённого соединения из Iroh-прототипа. Тест на двух экземплярах прерывает передачу, продолжает её с подтверждённого смещения и проверяет размер и хеш. |
| 3. Доступ в сеть | Сервер автоматически регистрирует устройство с действительным кодом приглашения. Проверки покрывают истечение срока, повтор и отзыв, права на публикации, обход путей и чтение выбранной версии. |
| 4. Конфигурация | `check`, `plan` и `apply` используют один разборщик и валидатор. Тесты различают синтаксические и семантические ошибки, проверяют три сценария из примера, общий фильтр `.venv`, фильтр GGUF только для ноутбука и сохранение ранее загруженных файлов. |
| 5. Двусторонний обмен | Тест с независимыми правками двух узлов проверяет сохранение обеих версий. Отдельно проверить конфликт удаления с правкой, распространение удаления по политике и повтор синхронизации. |
| 6. Приёмка выпуска | Собрать один Rust CLI для Windows и Linux. Выполнить сценарий от написания `network.sync` и подключения по коду до синхронизации и чтения истории. Оформить руководство со всеми поддерживаемыми конструкциями и воспроизводимыми командами. |

## Проверки выпуска

- `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked` и `cargo build --locked --release`.
- Один и тот же набор тестов на Windows и Linux. Для Linux подходят Docker, WSL или среда CI. Тесты транспорта используют локальные адреса. Живой обмен через VPN или релей проверяется отдельно на двух устройствах при действующих сетевых настройках.
- Интерфейс первой версии — терминальные команды с `--help`. Приглашение копируется как один код и вводится на новом устройстве. QR-код может представлять тот же код. Мобильное приложение идёт после приёмки настольной версии.

## Переход к равноправной сети

| Шаг | Критерий приёмки |
|---|---|
| Распределённый общий конфиг | Три зарегистрированных узла без постоянного сервера обмениваются настройками каждые несколько секунд. A меняет правило между B и C. Старая копия после возвращения офлайн-узла сохраняет новую правку. Независимые правки доступны для объединения. |
| Правила на уровне папок | На одной паре узлов направления для двух папок противоположны. Отдельная папка принимает новые файлы с сохранением существующих. Узел может участвовать в распространении настроек без синхронизации папок. |
| Вход через любого участника | Новый узел вводит один код, регистрируется у доступного участника и узнаёт об остальных, включая временно отключённых. Обращения к папкам проверяют права. Отдельно оценить единый код сети или мнемонику для обнаружения. |
| Индекс и передача | Единый логический индекс узла описывает версии и позволяет собрать очередь по правилам всех папок. Тест проверяет пакет мелких файлов, часть большого файла и восстановление после обрыва. |
| Производительность | После проверки корректности измерить загрузку канала и эффект параллельных передач. |

## Дальнейшие идеи

- Приложение для просмотра архива фотографий и скачивания выбранных версий.
- Лимиты хранения по возрасту и количеству версий с предварительным планом очистки.
- Условия передачи по типу подключения, заряду и расписанию.
- Несколько архивных копий папки. Определить правила подтверждения сохранения и восстановления после отказа узла.

Открытые решения для реализации — формат локального журнала, разбиение крупных файлов, поведение при нехватке диска и привязка каталога камеры на Android.
