# Как писать network.sync

`network.sync` — декларативная программа для Nice Sync. Она задаёт устройства, опубликованные папки, правила передачи и права. Nice Sync исполняет эти правила по командам `serve` и `sync`.

Рабочий пример со всеми видами обмена лежит в [examples/network.sync](../examples/network.sync). Сценарий первого подключения приведён в [README](../README.md#первое-подключение).

Если нужно просто запустить обмен или найти нужный файл настроек, начните с [инструкции для Windows и Arch](usage.md).

## Как отличить правило от команды

В терминале вы запускаете программу и даёте ей подкоманду. Например, `nice-sync --state "$HOME/.nice-sync" sync --share learn --follow-config` означает один запуск `nice-sync`. Здесь `sync` — подкоманда, а `--state`, `--share` и `--follow-config` — её параметры. PowerShell или Bash подставляет переменные и передаёт аргументы программе.

В `network.sync` вы пишете правила, которые программа читает сама. Вот реальное правило для зеркала:

```text
mirror linux at "/home/nikita/Documents/Учеба" on delete keep on conflict keep-both
```

| Часть правила | Что означает |
|---|---|
| `mirror` | Режим обмена в обе стороны |
| `linux` | Имя устройства, ранее объявленного как `device linux` |
| `at "/home/nikita/Documents/Учеба"` | Локальная папка именно этого устройства |
| `on delete keep` | Удаление файла не распространяется на другую сторону |
| `on conflict keep-both` | При независимых правках сохранить оба варианта |

Это одно правило с несколькими обязательными частями. Оно может занимать несколько строк. Парсер читает ключевые слова в определённом порядке и использует пробелы и переводы строк как разделители. Например, внутри `share` то же правило можно записать так:

```text
mirror linux at "/home/nikita/Documents/Учеба"
    on delete keep
    on conflict keep-both
```

Кавычки объединяют путь в одну строку, даже если в пути есть пробелы. Обратный слеш в конце строки для переноса не нужен. Фигурные скобки открывают и закрывают блоки. Точка с запятой в конце правила не используется.

## Структура

В файле один блок `network имя { ... }`. Внутри объявляйте устройства через `device имя`, папки через `share имя { ... }` и приглашения через `invitation имя { ... }`. Имя начинается со строчной латинской буквы. После неё допустимы строчные латинские буквы, цифры, дефис и подчёркивание. Максимальная длина — 63 символа. Имена уникальны внутри каждого вида объявлений. Комментарий начинается с `#` и продолжается до конца строки.

Каждая папка имеет ровно один `host устройство at "путь"`. Все публикации одной сети находятся на одном хосте. Для каждого другого устройства можно задать одно правило обмена на папку.

Пути в кавычках принадлежат указанному устройству. Для конфига, загруженного через `apply`, относительный путь считается от каталога файла. При получении общего конфига клиент отсчитывает относительные пути от рабочего каталога команды. Для Windows подходят `"D:/Docs"` и `"D:\\Docs"`. Для Linux подходит `"/home/alex/docs"`. Для общего конфига проще указывать абсолютные пути. Внутри кавычек язык не раскрывает `~` и переменные оболочки. Папки для `archive`, `receive` и `mirror` нужно создать заранее. Хост и `checkout` создают свои каталоги при запуске.

### Полный конфиг из одного примера

```text
network home {
    device windows
    device linux

    share learn {
        host windows at "C:/Users/pniki/Documents/Учеба"
        ignore directory "**/target"
        mirror linux at "/home/nikita/Documents/Учеба"
            on delete keep
            on conflict keep-both
    }

    invitation connect-linux {
        issued by windows
        grant browse, download, mirror on learn
        expires in 15m
        uses 1
    }
}
```

`home` — имя сети, `learn` — имя публикации, `connect-linux` — имя шаблона приглашения. Они используются в разных местах. Для обмена одной папкой выбирайте `sync --share learn`, для выдачи кода — `invite --template connect-linux --device linux`. Удалённый путь к файлу начинается с имени хоста и публикации, например `windows:/learn/notes.txt`. Физические пути на обоих устройствах задаются в `at`.

## Правила обмена

Начните с направления. `archive from` и `receive from` означают «взять у этого устройства и отправить хосту». `checkout` означает «забрать с хоста на это устройство». `mirror` выбирайте, если редактируете файлы с обеих сторон.

Записывайте правила в такой последовательности. Здесь `ИМЯ` и `ПУТЬ` — места для ваших значений, а `keep | propagate` означает выбор одного слова:

```text
host ИМЯ at "ПУТЬ"
archive from ИМЯ at "ПУТЬ" on delete keep on overwrite version
receive from ИМЯ at "ПУТЬ" on delete keep on overwrite version
checkout ИМЯ at "ПУТЬ"
mirror ИМЯ at "ПУТЬ" on delete keep | propagate on conflict keep-both
```

После любого правила обмена можно открыть блок `{ ... }` с его собственными `ignore`. `from` есть в `archive` и `receive`. Политики удаления и конфликта принадлежат правилу целиком. В `checkout` эти части отсутствуют.

| Запись внутри `share` | Действие |
|---|---|
| `archive from phone at "camera" on delete keep on overwrite version` | Отправляет фотографии на хост. Удаление на телефоне сохраняет архив. Новые байты по тому же пути образуют новую версию. |
| `receive from pc at "work" on delete keep on overwrite version` | Отправляет рабочую копию на хост и сохраняет прежние версии. Удаление на ПК сохраняет хостовую копию. |
| `checkout laptop at "work"` | Получает изменения с хоста. Удаление на хосте удаляет чистую локальную копию. При локальной правке Nice Sync сообщает о конфликтующем пути и сохраняет файл. |
| `mirror laptop at "docs" on delete propagate on conflict keep-both` | Синхронизирует обе стороны. Удаление распространяется, если другая сторона к этому моменту не изменила файл. |
| `mirror laptop at "docs" on delete keep on conflict keep-both` | Синхронизирует содержимое, сохраняя существующую копию на другой стороне при удалении. Следующий проход может восстановить удалённую локальную копию из актуальной версии хоста. |

В `mirror` конфликт определяется по общей базовой версии. При двух независимых правках текущая версия остаётся под исходным именем, а поступившая получает соседнее имя вида `notes.nice-conflict-<хеш>-1.txt`. Если на одной стороне файл удалили, а на другой изменили, изменённое содержимое сохраняется. `history` показывает номера версий, автора, базовую версию, BLAKE3 и отметки удаления. Отдельная запись файла конфликта содержит исходный путь в `base_path`.

## Исключения

При полном обходе хост пропускает файлы и поддеревья, исключённые на уровне сети или публикации. Ранее записанные версии сохраняются. Для исключённого файла, которого ещё нет в каталоге, используйте ручное скачивание по точному пути.

Общие `ignore` пишите внутри `network`. Правила для одной папки пишите внутри `share`. Правила устройства добавляйте в необязательный блок после его строки `archive`, `receive`, `checkout` или `mirror`. Исключения всех применимых уровней складываются.

```text
ignore directory "**/.venv"
checkout laptop at "work" {
    ignore file "**/*.gguf"
}
```

В примере правило `.venv` в блоке `network` исключит виртуальные окружения из автоматического обмена для всей сети. GGUF исключается из автоматического скачивания на ноутбук, а ПК может отправлять модели на хост.

Маски сопоставляются с относительным путём от корня публикации и учитывают регистр. Используйте `/` как разделитель. `*` сопоставляется с нулём или несколькими символами внутри одного компонента, `?` — с одним символом, `**` — с нулём или несколькими уровнями. Поэтому `**/*.gguf` подходит и для `model.gguf`, и для `models/model.gguf`. Правило `ignore directory` исключает совпавший каталог и всё его поддерево. Новый фильтр сохраняет ранее скачанные файлы. Ручное скачивание по праву `download` остаётся доступным.

| Маска | Что она охватит |
|---|---|
| `ignore directory "target"` | Только каталог `target` в корне |
| `ignore directory "**/target"` | Каталог `target` в корне и на любой глубине |
| `ignore file "*.tmp"` | Файлы `.tmp` в корне |
| `ignore file "**/*.tmp"` | Файлы `.tmp` на любой глубине |
| `ignore file "exports/report-?.pdf"` | Например, `exports/report-1.pdf`, а для `exports/report-10.pdf` нужны два символа или `*` |

## Права и приглашения

Публикация задаёт роли и каталоги. Права, выданные при регистрации ключа, определяют доступные операции.

| Право | Операция |
|---|---|
| `browse` | Перечислить публикации и вложенные папки, посмотреть историю. |
| `download` | Скачать файл или версию вручную. |
| `archive`, `receive` | Загружать файлы по соответствующей роли. |
| `checkout` | Получать изменения по роли `checkout`. |
| `mirror` | Загружать и получать изменения по роли `mirror`. |

Составить права для устройства можно одной или несколькими строками `permit`. Хост выдаёт их командой `invite --configured --device ноутбук`, где вместо `ноутбук` подставьте имя устройства из конфига.

```text
permit laptop browse, download, checkout on projects

invitation docs-laptop {
    issued by server, phone
    grant browse, download, mirror on docs
    expires in 15m
    uses 1
}
```

В шаблоне сначала перечислите выдающих код устройств в `issued by`, затем добавьте одну или несколько строк `grant`, срок `expires in` и `uses 1`. Срок указывается целым числом от `1m` до `10080m`. `on *` в строке `permit` или `grant` применяет права ко всем публикациям на момент выдачи. При регистрации по шаблону устройство получает права из `grant`. В примере код `docs-laptop` даёт доступ к `docs`, а код `--configured --device laptop` выдаёт доступ к `projects`.

Команда `invite --template docs-laptop --device laptop` выдаёт одноразовый код для нового устройства с именем `laptop`. Выпустить его может хост или зарегистрированное устройство, перечисленное в `issued by`. Новый узел вводит код в `join`. Хост привязывает ключ и права автоматически. Для входа, просмотра и ручного скачивания достаточно кода. Для автоматического обмена примените конфиг, который укажет локальные папки этого устройства. Повтор с уже зарегистрированного ключа до истечения срока восстанавливает результат предыдущей попытки. Другой ключ с тем же кодом получает ошибку. Команда `revoke laptop` на хосте отзывает права ключа и аннулирует коды для этого имени, включая уже выданные.

В строке `grant browse, download, mirror on learn` слова до `on` перечисляют операции через запятую. `on learn` ограничивает их публикацией `learn`. В `issued by windows` указано, кто может выпустить код. Имя получателя выбирается параметром `--device` при выдаче. `permit` задаёт набор для выдачи через `invite --configured`, а `grant` в шаблоне — для выдачи через `invite --template`. Изменение `grant` или `permit` применяется к новым кодам, а уже выданные права хранятся в реестре.

## Проверка, применение и запуск

| Подкоманда | В чём её задача |
|---|---|
| `check ФАЙЛ` | Проверить синтаксис, имена и политики без применения |
| `plan ФАЙЛ --device ИМЯ` | Показать, какие пути, роли и фильтры получит устройство |
| `apply ФАЙЛ --device ИМЯ` | Сохранить проверенный снимок настроек и путь к файлу в состоянии |
| `serve --share-config` | Запустить хост, раздавать общий конфиг и перечитывать его при сохранении |
| `invite --template ШАБЛОН --device ИМЯ` | Выпустить код по объявленному шаблону |
| `join` | Прочитать код и зарегистрировать ключ устройства. `--sync` запускает первый проход с общим конфигом |
| `sync` | Выполнить один проход. `--follow-config` получает правила с хоста, `--every 10` повторяет обмен |
| `ls`, `history`, `get` | Посмотреть доступные папки, узнать версии, скачать файл или версию |
| `browse [АДРЕС]` | Открыть удалённый просмотр с `cd`, `ls`, `pwd` и `exit` |

Если диагностика сообщает `6:25: syntax: invalid escape`, откройте строку 6 и посмотрите строку в кавычках около столбца 25. Частая причина в Windows — путь вида `"C:\Users\alex"`. Запишите его как `"C:/Users/alex"`. Если написано `semantic: unknown device 'laptop'`, имя распознано, но для него нужно добавить `device laptop` либо исправить опечатку. После `check` используйте `plan --device windows` или `plan --device linux`, чтобы увидеть фактический путь для конкретного устройства.

Хост может раздавать единый конфиг зарегистрированным устройствам. Примените файл на хосте и запустите `serve --share-config`. Новый клиент выполняет `join --sync` для первой синхронизации. Уже зарегистрированный клиент запускает `sync --follow-config --every 10`. Перед каждым проходом он получает применённый текст с хоста и сохраняет копию в `shared.sync` внутри своего каталога состояния.

Для проекта cadcraft скрипт [scripts/connect-linux.sh](../scripts/connect-linux.sh) собирает текущий клон, устанавливает программу в `~/.local/bin` и создаёт `~/Downloads/cadcraft`. Для сборки нужны Cargo и компилятор `cc`. После `git pull --ff-only` запустите `bash scripts/connect-linux.sh`. Вставьте код при первом запуске. Для повторного запуска используйте прежний каталог состояния (`~/.nice-sync` по умолчанию или `--state путь`). Скрипт синхронизируется каждые 10 секунд в текущем терминале. Флаг `--once` выполняет один проход.

Эти флаги разрешают использовать локальные пути из конфига хоста. Для общей конфигурации удобны абсолютные пути. Относительные пути клиент отсчитывает от текущего каталога команды. Создайте папки для `mirror`, `archive` и `receive` заранее.

Редактируйте файл, который передали в `apply` на хосте. `serve --share-config` проверяет этот файл примерно раз в секунду, применяет корректную правку и отдаёт её клиентам в следующем цикле обмена. При ошибке хост пишет причину в терминал и продолжает использовать последнюю рабочую версию. Имя хоста и сети остаются прежними. Клиентская копия `shared.sync` перезаписывается при обмене. Если состояние хоста создано старой сборкой, один раз примените исходный файл новой сборкой и запустите хост.

При замене корня публикации на другую папку хост открывает для неё отдельный архив. Если вы переключаете синхронизацию на другой набор файлов, укажите также новый локальный корень устройства. Журнал прежнего корня сохраняется и снова доступен при возврате к этому корню.

`serve` готов принимать подключения после сообщения `Serving`. Хост индексирует файлы при формировании снимка для синхронизации. `ls` без пути показывает публикации. Для `ls` с путём и интерактивного `browse` хост читает только запрошенный каталог, включая пустой. Файлы для просмотра не индексируются.

### Просмотр без автоматического обмена

Добавьте внутри `network` публикацию с одним `host`. Вложенные папки доступны через неё по мере навигации:

```text
share downloads {
    host windows at "C:/Users/pniki/Downloads"
}
```

Для нового подключения включите в приглашение `grant browse on downloads` или выдайте настроенное право через `permit linux browse on downloads` и `invite --configured`. Это разрешает просмотр. Для скачивания добавьте `download`. Существующая регистрация сохраняет прежние выданные права, поэтому новую публикацию нужно явно включить в права нового приглашения. Корни публикаций одного хоста должны быть раздельными.

Запустите `nice-sync browse windows:/downloads`. Внутри просмотра команда `cd Папка` запрашивает её непосредственное содержимое, `ls` перечитывает текущий уровень, `cd ..` поднимается на уровень выше, а `cd /` открывает список доступных публикаций. `pwd` показывает текущий удалённый адрес. Команды `ls Папка` и `cd Папка с пробелами` тоже поддерживаются. `exit` завершает просмотр. Хост проверяет право `browse`, отклоняет выход за опубликованный корень и пропускает ссылки. При просмотре также действуют исключения сети и публикации.

При первом обмене `sync` показывает обход папки и ход передачи. Обновлённый клиент строит локальный индекс и получает индекс хоста до начала передачи данных. Он сравнивает версии и упаковывает нужные данные в блоки до 8 МиБ или 512 записей. Это работает в обоих направлениях. В пакете могут находиться небольшие файлы целиком и части больших файлов. После обрыва передача возобновляется с последнего сохранённого смещения. При соединении со старым хостом клиент использует прежний протокол.

Чтобы увидеть маршрут передачи, запустите `sync --show-route` или `bash scripts/connect-linux.sh --show-route`. Строка `Nice Sync route` показывает текущий IP или релей Iroh и оценку RTT. При смене маршрута появляется новая строка. Если клиенту доступен UDP-адрес хоста по локальной сети или VPN, `sync --direct IP:PORT` и одноимённый флаг скрипта позволяют использовать его. Ключ хоста и сохранённая регистрация остаются прежними. По умолчанию клиент по-прежнему выбирает маршрут автоматически.

`sync --p2p-only` и одноимённый флаг скрипта оставляют релей для установления связи. После появления прямого пути клиент открывает новое соединение с тем же ключом хоста и локальным UDP-портом. Для этого соединения релей отключён. Если прямой путь не появился за 20 секунд или прямое подключение не удалось, проход откладывается до следующей попытки. Периодический режим повторяет попытки и продолжает с сохранённых данных. Если прямой UDP недоступен между устройствами, в этом режиме файлы будут ждать его появления.

```sh
nice-sync check network.sync
nice-sync --state .nice-sync/laptop plan network.sync --device laptop
nice-sync --state .nice-sync/laptop apply network.sync --device laptop
```

`check` проверяет синтаксис, ссылки и политики. Диагностика указывает строку и столбец, например `3:23: semantic: unknown device 'other'`. `plan` показывает разрешённые пути и фильтры указанного устройства. На хосте в план также попадают права и шаблоны. `apply` повторяет проверку и атомарно сохраняет снимок конфига в каталог состояния. Для применения другого файла через `apply` остановите текущий `serve` или `sync --every` на соответствующем устройстве. Выданные права сохраняются до отзыва.

```sh
nice-sync --state .nice-sync/laptop sync --share docs
nice-sync --state .nice-sync/laptop ls server:/
nice-sync --state .nice-sync/laptop ls server:/docs
nice-sync --state .nice-sync/laptop history server:/docs/notes.txt
nice-sync --state .nice-sync/laptop get server:/docs/notes.txt notes-v1.txt --version 1
```

Удалённый путь имеет вид `имя-хоста:/имя-публикации/путь`. Имена файлов должны быть переносимыми между Windows и Linux. Nice Sync пропускает ссылки при обходе и отклоняет пути с выходом из опубликованного дерева. Синхронизируются обычные файлы. Каталоги появляются при записи файлов. История и проверенные объекты остаются в каталоге состояния хоста. Размер ответа с индексом ограничен 8 МиБ. Ручное скачивание поддерживает блоки по 1 МиБ с возобновлением по сохранённому смещению.
